Wat is JSON Schema?

JSON schema is een 'schema' dat aangeeft hoe JSON data moet opgesteld zijn.

Het beschrijft de hiërarchie, attributen, types en extra validatieregels (patroon, min/max waarde, enz.)

Voornamelijk gebruikt voor REST API calls te valideren (client & server side).

Geeft een 'flexibel contract' waaraan voldaan moet worden.

XML Schema vs JSON Schema

Binnen APO gebruiken we XML schemas die valideren dat een XML bestand juist is opgemaakt.

Hoewel XSD voor XML en JSON Schema voor JSON bedoeld zijn, zijn er key differences:

Verschillen met XSD

  • Element volgorde: XML Schemas kunnen afdwingen welk element voor een ander komt. JSON Schema kan dit niet, maar we hebben dit niet nodig.
  • Data types: XML heeft meer standaard formaten (Date, Time). JSON Schema heeft JavaScript primitives, maar kan uitgebreid worden met 'format'.
  • Namespaces: XML gebruikt namespaces om elementen te onderscheiden. JSON Schema heeft geen ingebouwde namespace ondersteuning, maar kan dit simuleren met conventies.

Verschillen met XSD ...

  • Conditionele logica: XSD 1.1 ondersteunt “als... dan...” via assert. Bij JSON schema is extractie eenvoudiger.
  • Combinatorische logica: Beiden ondersteunen dit, maar extractie is bij JSON schema makkelijker.
  • Leesbaarheid: JSON schema is vaak compacter en makkelijker manueel te lezen/onderhouden dan XSD.

Voorbeelden - Basis validatie

{
  "type": "object",
  "properties": {
    "naam": { "type": "string", "title": "Naam" },
    "leeftijd": { "type": "integer", "minimum": 18, "title": "Leeftijd" }
  },
  "required": ["naam"]
}

Geldige JSON

{
  "naam": "Jan Janssen",
  "leeftijd": 25
}
{
  "naam": "Marie Peeters"
}

❌ Ongeldig: { "leeftijd": 25 } (naam verplicht)

❌ Ongeldig: { "naam": "Piet", "leeftijd": 16 } (minimum 18)

Voorbeelden - Keuzelijst

{
  "type": "object",
  "properties": {
    "status": {
      "type": "string",
      "enum": ["nieuw", "in_behandeling", "afgesloten"],
      "title": "Status dossier"
    }
  },
  "required": ["status"]
}

Geldige JSON

{
  "status": "nieuw"
}
{
  "status": "in_behandeling"
}

❌ Ongeldig: { "status": "voltooid" } (niet in enum)

Voorbeelden - Conditionele validatie

{
  "type": "object",
  "properties": {
    "isStudent": { "type": "boolean", "title": "Is student?" },
    "studentennummer": { "type": "string", "title": "Studentennummer" }
  },
  "if": { "properties": { "isStudent": { "const": true } } },
  "then": { "required": ["studentennummer"] }
}

Geldige JSON

{
  "isStudent": true,
  "studentennummer": "r0123456"
}
{
  "isStudent": false
}

❌ Ongeldig: { "isStudent": true } (studentennummer verplicht als isStudent=true)

Voorbeelden - Lijsten

{
  "type": "object",
  "properties": {
    "contacten": {
      "type": "array",
      "title": "Contactpersonen",
      "items": {
        "type": "object",
        "properties": {
          "naam": { "type": "string" },
          "email": { "type": "string", "format": "email" }
        },
        "required": ["naam"]
      }
    }
  }
}

Geldige JSON

{
  "contacten": [
    { "naam": "Jan", "email": "jan@example.com" },
    { "naam": "Marie" },
    { "naam": "Piet", "email": "piet@example.com" }
  ]
}

❌ Ongeldig: { "contacten": [{ "email": "test@example.com" }] } (naam verplicht)

Combinatorische logica

JSON Schema biedt combiners om regels te combineren of conditioneel toe te passen.

De belangrijksten: allOf, anyOf, oneOf, not

Deze kunnen overal in het schema voorkomen (root, properties, enz.)

allOf: "Alles moet geldig zijn"

{
  "allOf": [
    {
      "properties": { "naam": { "type": "string" } },
      "required": ["naam"]
    },
    {
      "properties": {
        "leeftijd": { "type": "integer", "minimum": 18 }
      }
    }
  ]
}

Geldige JSON

{
  "naam": "Jan Janssen",
  "leeftijd": 25
}
{
  "naam": "Marie Peeters"
}

❌ Ongeldig: { "leeftijd": 25 } (naam verplicht)

anyOf: "Eender welke moet geldig zijn"

{
  "anyOf": [
    { "required": ["email"] },
    { "required": ["telefoon"] }
  ],
  "properties": {
    "email": { "type": "string", "format": "email" },
    "telefoon": { "type": "string" }
  }
}

Geldige JSON

{
  "email": "jan@example.com"
}
{
  "telefoon": "0123456789"
}
{
  "email": "jan@example.com",
  "telefoon": "0123456789"
}

❌ Ongeldig: {} (email of telefoon verplicht)

oneOf: "Exact één moet geldig zijn"

{
  "oneOf": [
    {
      "properties": { "type": { "const": "persoon" }, "naam": { "type": "string" } },
      "required": ["type", "naam"]
    },
    {
      "properties": { "type": { "const": "organisatie" }, "bedrijfsnaam": { "type": "string" } },
      "required": ["type", "bedrijfsnaam"]
    }
  ]
}

Geldige JSON

{
  "type": "persoon",
  "naam": "Jan Janssen"
}
{
  "type": "organisatie",
  "bedrijfsnaam": "ACME Corp"
}

❌ Ongeldig: { "type": "persoon", "naam": "Jan", "bedrijfsnaam": "ACME" } (beide schemas geldig)

not: "Dit mag niet geldig zijn"

{
  "not": {
    "properties": {
      "status": { "const": "afgesloten" },
      "openTaken": { "minimum": 1 }
    },
    "required": ["status", "openTaken"]
  }
}

(Externe) referenties & bundles

JSON schemas leven vaak op het WWW in REST APIs.

$ref keyword voorkomt herhaling door modellen te hergebruiken.

Interne referentie

{
  "$defs": {
    "Persoon": {
      "type": "object",
      "properties": {
        "naam": { "type": "string" },
        "email": { "type": "string", "format": "email" }
      },
      "required": ["naam"]
    }
  },
  "properties": {
    "aanvrager": { "$ref": "#/$defs/Persoon" },
    "contactpersoon": { "$ref": "#/$defs/Persoon" }
  }
}

Externe referentie

Schema persoon.schema.json:

{
  "$id": "https://example.org/schemas/persoon.schema.json",
  "type": "object",
  "properties": {
    "id": { "type": "string" },
    "naam": { "type": "string" }
  },
  "required": ["id", "naam"]
}

Gebruik in ander schema

{
  "properties": {
    "eigenaar": { "$ref": "https://example.org/schemas/persoon.schema.json" }
  }
}

Geneste externe referentie

{
  "properties": {
    "aanvrager": { "$ref": "https://example.org/schemas/contact.schema.json#/$defs/Persoon" },
    "adres": { "$ref": "https://example.org/schemas/contact.schema.json#/$defs/Adres" }
  }
}

RIE-IEPR Implementatie

JSON Schema wordt in de merge request onderverdeeld in drie luiken:

  1. De schema(s) zelf
    SOSA/SSN properties voor observaties
  2. Validatie van JSON documenten
    Controleren of data correct is
  3. Extractie van info voor UI generatie
    Automatisch spreadsheets en formulieren genereren

RIE-IEPR Implementatie - Luik 1

De schema(s) zelf

We gebruiken properties die aansluiten bij SOSA en SSN:

  • SOSA = Sensor, Observation, Sampling and Actuator
  • SSN = Semantic Sensor Network

Vaste specificaties, ook buiten dOMG gebruikt (bijv. luchtwassers)

SOSA/SSN - Hoe werkt het?

Observatie model:

  • Sensor: Het instrument dat de meting uitvoert (bijv. temperatuurmeter)
  • Observation: De meting zelf op een bepaald tijdstip
  • ObservableProperty: Wat er gemeten wordt (bijv. temperatuur, pH-waarde)
  • Result: De uitkomst van de meting (waarde + eenheid)
